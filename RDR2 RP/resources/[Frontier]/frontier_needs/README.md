# Phase 2: Frontier Needs and session ammunition recovery

## Deployment (test server)
Back up the database and deploy every changed resource. Apply frontier_needs/sql/migrations/001_needs.sql once. Actual host server.cfg is not tracked; remove ensure/start vorp_metabolism (and blanket ensure [VORP]), stop it permanently, add ensure frontier_needs after frontier_inventory and before frontier_hud. Full server restart with players disconnected. Retain VORP Core/Character and Stables as in Phase 1. No changes to old VORP needs tables; new needs start at 100% once, then persist. Do not run both needs engines.

## Needs
Server-owned values 0..1000. Online decay only, every 15 seconds, configurable; faster movement increases food/water/energy drain when server movement natives are available. Energy recovers while resting; low energy caps the native stamina core, zero food/water damages the player. Observed death followed by respawn resets needs. HUD retains native health, endurance and Dead Eye and adds Energy. Existing four consumables keep their nutritional values; energy bonuses and decay are initial balancing choices. A 3-second server consumption cooldown, outbox + completed inventory receipt and atomic applied marker prevent effect duplication; unfinished consumption requests never apply. The effect survives a restart, even if the cosmetic animation does not. On-foot unarmed consumption plays a bounded best-effort animation; props, pre-consume timed interaction and medical effects are not implemented. Native animations, damage and server movement detection need live verification. Legacy body-weight/appearance metabolism effects not ported.

## Ammo
Normal holster/switch retains rounds for the session. Draw checkout and ammo debits now update durable weapon metadata atomically with the inventory transaction; decreases observed by client are checkpointed on server. On next login (also after server restart), all carried equipped/satchel weapons are unloaded, with rounds returned to compatible quick slots first, then satchel. Full inventory sends overflow to private persistent pending ammo; use /frontierclaimammo after making room, or reconnect. Inventory shows pending count. Ground, trade and warehouse weapons are outside the personal-session scan. Recovery runs before inventory access; each transfer clears/reduces its source atomically, so replay/restart cannot refund the same stored rounds twice. A disconnected player receives the last persisted count, not an unverifiable final client count; shots after the final checkpoint can be refunded, and a failed native grant can still lose rounds. This is not full anti-cheat. Old already-forfeited rounds cannot be reconstructed. No extra inventory schema migration.

## Acceptance checks
Test loaded holster and switch; partially fired gun reconnect while drawn and while holstered; both guns; full belt then satchel; full inventory overflow, claim and repeated relog; normal shutdown; check total ammo conservation and no duplicate credits. Food via wheel and inventory, clamp at 100%, hunger/thirst/energy decay, rest and running, zero needs and respawn, logout/reconnect persistence, queued receipt replay and failed inventory transaction, HUD values and resource stop. Existing VORP Metabolism must remain stopped. No live RedM or database integration tests performed during authoring.
