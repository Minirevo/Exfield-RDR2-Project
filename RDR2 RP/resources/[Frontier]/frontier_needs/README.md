## Fuel-chain needs (replaces the initial decay design)
Apply sql/migrations/002_stamina.sql after 001 (existing deployments need only 002). Preserves existing hunger/thirst/energy and initializes stamina full. MariaDB ADD COLUMN IF NOT EXISTS. Restart frontier_needs and frontier_hud, preferably full restart. No other SQL changes.

Server ticks every 2 seconds. Basal loss every 10 seconds: 0.1 percentage points food, 0.2 water. On-foot sprint drains 4% stamina per tick (~50 seconds from full), jog 0.8%, swim 3%. Sprint locks at zero, unlocks at 20%. Standing recovers 5% stamina per tick, walking 2.4%. Restoring stamina costs energy at 4:1 (rounded per step). Only once stamina is recovered or energy is exhausted can nutrition rebuild energy while resting/walking/mounted. Recovery spends both food and water; no direct nutrition penalty for sprinting beyond basal loss. New food/drink uses no longer directly boost energy; queued older effects retain their already-recorded amounts. Below 20% energy or hydration, attainable stamina falls towards 25%. At zero energy, recovery can rebuild a little energy then spend it on stamina; if either nutrition reserve is empty no energy recovery. Online only; all four values persist. Stale activity hints don't grant rest recovery. Server controls the amounts; client movement hints plus server speed are not a full anti-cheat. Native combat stamina remains active independently; the sprint block disables INPUT_SPRINT only when on foot, not horse sprint. Actual running detection, sprint controls and death damage need RedM testing. Server-side character death-state fix included (no zero-health fallback). Observed death/respawn resets all values.

At zero food: 2% max-health damage per 15 seconds. At zero water: 3%. Combined 5%; roughly 5 minutes from full health if both remain empty, ignoring other health effects. Client applies only server-requested bounded damage. No instant death or automatic health restoration. Existing consumption outbox remains durable; 3-second cooldown and best-effort cosmetic eating/drinking animation retained. No VORP Metabolism or VORP inventory dependency. VORP Core still provides character death state. Sleeping, labour and fitness integration are not yet implemented.

Use /frontierneedsstatus for raw values, activity, cap and sprint lock. All rates configurable in config.lua; starting balance deliberately conservative. Test fixture: from frontier_needs, run lua5.4 tests/model.lua. Tests cover sprint depletion, lock/recovery, nutrition costs, no fuel when empty, basal drain and additive damage.

## Ammo
Normal holster/switch retains rounds for the session. Draw checkout and ammo debits now update durable weapon metadata atomically with the inventory transaction; decreases observed by client are checkpointed on server. On next login (also after server restart), all carried equipped/satchel weapons are unloaded, with rounds returned to compatible quick slots first, then satchel. Full inventory sends overflow to private persistent pending ammo; use /frontierclaimammo after making room, or reconnect. Inventory shows pending count. Ground, trade and warehouse weapons are outside the personal-session scan. Recovery runs before inventory access; each transfer clears/reduces its source atomically, so replay/restart cannot refund the same stored rounds twice. A disconnected player receives the last persisted count, not an unverifiable final client count; shots after the final checkpoint can be refunded, and a failed native grant can still lose rounds. This is not full anti-cheat. Old already-forfeited rounds cannot be reconstructed. No extra inventory schema migration.

## Labour integration
Apply 003_labour.sql before starting updated Needs. Gathering/blacksmithing, hunting/fishing (where the native integrations are enabled), farming and manual station batches check stamina before starting and debit once at validated completion. Costs are configured per resource/activity in config.lua; each production batch counts separately. NPC orders and reward recovery do not spend player stamina. Debits are atomic with their own idempotency receipt, but not with the subsequent farm/gather/station transaction: an interrupted downstream DB operation can cost stamina without a reward. Stamina is never directly converted to food/water loss. Medical V1 blocks labour when unconscious or an unstabilised fracture is present. Sleeping and skill discounts are deferred. Native idle detection now prefers fresh stationary samples; declining capacity limits new recovery without actively draining existing stamina.

When Frontier Medical is started, starvation/dehydration are server-side physiological deprivation instead of native HP damage; the old native consequence is only a standalone fallback when Medical is stopped.
